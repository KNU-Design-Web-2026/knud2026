# ADR-0002: UI 문서화와 시각 검수에 Storybook과 Chromatic을 사용한다

- 상태: 승인됨
- 결정일: 2026-07-16
- 적용 범위: 공통 UI, 주요 화면 상태, 인터랙션, 반응형 시각 검수

## 배경

이 프로젝트는 피그마를 기반으로 개발자 한 명이 구현하지만 디자이너와 지속적으로 화면을 검수해야 한다. 특히 다음 항목은 완성된 페이지 한 장만으로 합의하기 어렵다.

- 1920px부터 모바일까지의 반응형 레이아웃
- 사자 눈동자 추적과 영상 전환
- 스크롤에 따른 폭탄, 경고창, 콘셉트 소개 전환
- 팀 사진 드래그 갤러리
- 작품·작가 데이터의 길이와 누락 여부에 따른 상태
- 롤링페이퍼의 작성, 접힘, 배치, 빈 상태, 긴 내용

Markdown 문서만으로는 실제 UI 상태를 재현할 수 없고, 배포된 전체 페이지에서만 검수하면 작은 컴포넌트의 상태와 회귀를 확인하기 어렵다. 반대로 Storybook이나 Chromatic의 댓글만으로 질문과 결정 이유를 관리하면 특정 빌드에 기록이 묶이고 전체 맥락을 찾기 어렵다.

## 결정

UI 문서화와 검수 역할을 다음과 같이 분리한다.

| 대상 | 역할 |
|---|---|
| 저장소 Markdown | 질문, 답변, 결정 이유, 요구사항의 기록 |
| Storybook | 컴포넌트와 화면 조각의 재현 가능한 상태 및 인터랙션 예시 |
| Chromatic | 스토리의 시각적 기준선, 변경 비교, 디자이너 UI 검수 |
| E2E 테스트 | 실제 라우팅, 스크롤, 영상, API, DB를 포함한 전체 흐름 |

- 스토리 파일은 구현 파일 가까이에 `*.stories.tsx` 이름으로 둔다.
- 스토리는 기본 상태뿐 아니라 로딩, 빈 상태, 오류, 긴 콘텐츠, 모바일 등 의미 있는 변형을 표현한다.
- 인터랙션 스토리는 가능한 경우 `play` 함수를 사용해 클릭, 입력, 키보드 동작과 결과를 검증한다.
- Chromatic은 모든 애니메이션 프레임을 비교하지 않고 결정적인 정지 상태를 기준선으로 저장한다.
- 지속적으로 움직이는 UI는 테스트 전용 제어값으로 진행 상태를 고정하거나 시각 캡처 중 모션을 비활성화한다.
- 디자이너와 합의한 시각 변경만 새 기준선으로 승인한다.
- 일반 Q&A와 최종 의사결정은 `docs/design/`과 ADR에 남기며 Chromatic 댓글을 단일 기록으로 사용하지 않는다.

## 선정 이유

### 1. 구현된 UI 상태를 문서와 테스트로 함께 사용할 수 있다

Storybook의 스토리는 컴포넌트의 특정 속성값(props)과 상태를 독립적으로 렌더링한다. 같은 스토리를 개발 중 미리보기, 문서, 렌더 테스트, 인터랙션 테스트, 시각 테스트에 재사용할 수 있다.

### 2. 디자이너가 전체 개발 환경 없이 결과를 검수할 수 있다

게시된 Storybook과 Chromatic 검수 링크를 통해 디자이너는 변경 전후 화면을 비교하고 상태별 의견을 남길 수 있다. 피그마와 구현 결과 사이의 차이를 PR 단위로 확인할 수 있다.

### 3. 반응형과 예외 상태의 누락을 줄일 수 있다

중요 viewport와 콘텐츠 변형을 스토리로 고정하면 이후 수정에서 특정 너비, 긴 제목, 이미지 없음, 빈 롤링페이퍼 같은 상태가 깨지는지 반복해서 확인할 수 있다.

### 4. 시각 회귀를 자동으로 발견할 수 있다

Chromatic은 새 빌드의 스냅샷을 승인된 기준선과 비교한다. 공통 스타일이나 컴포넌트 변경이 다른 화면에 미친 영향을 PR에서 확인할 수 있다.

### 5. 1인 개발에서도 검수 과정의 기억 의존도를 낮춘다

구현자와 검수자가 적을수록 이전 상태와 합의 내용을 기억에 의존하기 쉽다. 문서, 스토리, 시각 기준선을 연결하면 시간이 지난 뒤에도 변경 이유와 기대 화면을 재현할 수 있다.

## 스토리 작성 우선순위

모든 작은 컴포넌트에 스토리를 의무화하지 않는다. 다음 순서로 작성한다.

1. 여러 화면에서 재사용하는 공통 UI
2. 디자이너 검수가 필요한 시각 요소
3. 상태가 여러 개인 인터랙티브 컴포넌트
4. 반응형에서 구조가 바뀌는 컴포넌트
5. 회귀 위험이 높은 롤링페이퍼 및 관리자 UI

단순한 정적 래퍼나 한 곳에서만 사용되고 별도 상태가 없는 요소는 스토리 대상에서 제외할 수 있다.

## 검수 기준 viewport

디자이너가 제시한 다음 너비를 주요 시각 확인 대상으로 사용한다.

- 1920px
- 1350px
- 1020px
- 600px
- 400px

모든 스토리에 다섯 viewport를 적용하지 않는다. 레이아웃 변화가 있는 스토리만 필요한 너비를 선택하고, 공통 최소 기준은 프로젝트 리뷰 컨벤션을 따른다.

## 한계와 대응

### 연속 애니메이션과 영상 전체를 픽셀 비교하기 어렵다

눈동자 이동, 드래그 관성, 영상 프레임처럼 매 실행 결과가 달라지는 동작은 시각 비교가 불안정하다. 시작, 전환 직전, 전환 직후, 완료 상태를 고정된 스토리로 만들고 전체 흐름은 E2E와 수동 검수로 확인한다.

### 실제 페이지 문맥과 데이터 연결을 완전히 대체하지 않는다

Storybook은 격리된 UI 검수에 사용한다. 실제 스크롤, 라우팅, API, DB 저장, 관리자 삭제는 통합 환경과 E2E 테스트에서 확인한다.

### 스토리 유지 비용이 발생한다

의미 있는 상태와 회귀 위험이 높은 컴포넌트부터 작성한다. 구현과 맞지 않는 스토리는 방치하지 않고 해당 기능 변경과 같은 PR에서 갱신한다.

### 외부 서비스 의존과 사용 비용이 생길 수 있다

Chromatic 프로젝트 범위와 빌드 빈도를 제한하고, 비용이나 운영 제약이 커지면 Storybook 정적 배포와 다른 시각 테스트 도구를 재검토한다. Markdown과 스토리는 저장소에 남으므로 의사결정 기록이 Chromatic에 종속되지 않는다.

## 도입 시점

- Next.js 애플리케이션을 생성한 뒤 Storybook 호환성과 현재 권장 구성을 확인한다.
- 첫 공통 UI와 주요 인터랙션을 구현할 때 Storybook을 설정한다.
- 디자이너가 검수할 핵심 스토리가 준비되면 Chromatic 프로젝트와 PR 검수를 연결한다.
- 정확한 버전, 애드온, CI 설정은 애플리케이션 초기화 계획에서 확정한다.

## 결과

### 기대 효과

- 디자인 질문과 구현 결과의 연결이 쉬워진다.
- UI 상태와 반응형 기준을 반복해서 재현할 수 있다.
- PR마다 의도하지 않은 시각 변화를 확인할 수 있다.
- 디자이너가 상태별 화면을 직접 검수할 수 있다.

### 감수하는 비용

- 스토리 작성과 모의 데이터 관리가 필요하다.
- 동적 애니메이션을 결정적인 상태로 분리해야 한다.
- Chromatic 빌드와 기준선 승인 과정을 운영해야 한다.
