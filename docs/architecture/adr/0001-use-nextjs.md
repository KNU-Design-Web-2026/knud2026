# ADR-0001: 웹 애플리케이션 프레임워크로 Next.js를 사용한다

- 상태: 승인됨
- 결정일: 2026-07-16
- 적용 범위: 2026 경북대학교 디자인학과 졸업전시 웹사이트

## 배경

이 프로젝트는 졸업전시와 작품을 소개하는 공개 웹사이트다. 주요 요구사항은 다음과 같다.

- 전시 안내, 작품 목록, 작품 상세, 작가 정보를 제공한다.
- 작품과 작가 데이터는 개발자가 저장소의 데이터 파일로 관리하고 재배포한다.
- 검색엔진과 SNS 공유에서 작품별 제목, 설명, 대표 이미지를 정확하게 노출해야 한다.
- 메인 화면에는 마우스 추적, 스크롤 및 캐릭터 애니메이션과 같은 클라이언트 인터랙션이 포함된다.
- 롤링페이퍼는 하나의 공용 게시판이며, 방문자가 로그인하지 않고 수신 작가를 선택해 편지를 작성한다.
- 작성된 편지는 데이터베이스에 저장되고 즉시 공개된다.
- 운영자는 경량 관리자 화면에서 부적절한 편지를 삭제 또는 숨김 처리한다.
- 개발과 운영은 한 명의 개발자가 담당한다.

따라서 이 프로젝트는 완전한 정적 사이트도, 복잡한 독립 백엔드 서비스도 아니다. 대부분의 콘텐츠는 빌드 시 생성할 수 있지만 롤링페이퍼와 관리자 기능에는 서버 실행 환경과 데이터베이스가 필요하다.

## 결정

프론트엔드와 경량 서버 기능을 **Next.js App Router 기반의 단일 애플리케이션**으로 구현한다.

- 언어는 TypeScript를 사용한다.
- 전시, 작품, 작가 페이지는 정적 생성 중심으로 구현한다.
- 마우스 추적과 애니메이션처럼 브라우저 상태가 필요한 부분만 Client Component로 구현한다.
- 작품과 작가 정보는 저장소의 타입이 정의된 데이터 파일로 관리한다.
- 롤링페이퍼 조회·작성 및 관리자 편지 숨김 기능은 Route Handler 또는 Server Function으로 구현한다.
- 편지는 관계형 데이터베이스에 저장한다.
- 관리자 기능은 별도 CMS가 아니라 인증된 편지 목록과 숨김 기능으로 제한한다.
- 초기 단계에서는 NestJS 애플리케이션과 프론트엔드·백엔드 모노레포를 만들지 않는다.

Next.js는 React를 대체하는 기술이 아니라 React를 기반으로 라우팅, 렌더링, 서버 기능, 메타데이터 관리를 통합한 프레임워크다. React 공식 문서도 새로운 React 앱과 웹사이트에는 프레임워크로 시작하는 방식을 권장한다.

## 선정 이유

### 1. 정적 전시 콘텐츠와 동적 롤링페이퍼를 한 애플리케이션에서 처리할 수 있다

전시·작품·작가 정보는 요청마다 서버에서 계산할 필요가 없다. 빌드 시 HTML을 생성하면 초기 응답이 빠르고 서버 부하가 작다. 반면 롤링페이퍼는 편지를 저장하고 최신 내용을 조회해야 하므로 동적 서버 처리가 필요하다.

Next.js는 페이지별로 정적 렌더링과 동적 서버 처리를 함께 구성할 수 있다. 작품 상세 페이지는 `generateStaticParams`로 빌드 시 생성하고, 롤링페이퍼 API는 Route Handler로 분리한다. 두 종류의 요구사항을 위해 별도의 프론트엔드와 API 서버를 운영할 필요가 없다.

### 2. 작품별 SEO와 SNS 공유 정보를 일관되게 관리할 수 있다

졸업전시 사이트는 작품명이나 작가명으로 검색했을 때 해당 상세 페이지가 노출되고, 링크 공유 시 작품별 대표 이미지와 설명이 표시되는 것이 중요하다.

Next.js의 Metadata API와 파일 규칙을 사용하면 페이지별 제목, 설명, Open Graph 이미지, 파비콘, `robots.txt`, `sitemap.xml`을 라우트 구조와 함께 관리할 수 있다. 이를 React SPA에서 직접 구성할 때 필요한 라우팅·사전 렌더링·메타데이터 도구의 추가 선택을 줄인다.

### 3. 인터랙션이 많은 화면도 React Client Component로 구현할 수 있다

정적 생성은 인터랙션이 없는 사이트를 의미하지 않는다. 눈동자 마우스 추적, 스크롤 기반 장면 전환, 필터, 모바일 메뉴 등은 필요한 컴포넌트만 클라이언트에서 실행하도록 분리한다.

정적인 작품 정보까지 모두 클라이언트 JavaScript로 처리하지 않고, 상호작용이 필요한 경계만 Client Component로 두어 초기 JavaScript 범위를 통제할 수 있다.

### 4. 롤링페이퍼 규모에는 독립 NestJS 서버가 필요하지 않다

현재 동적 서버 요구사항은 다음 범위다.

- 공개 편지 목록 조회
- 익명 편지 작성
- 입력값 검증과 요청 횟수 제한
- 관리자 인증
- 관리자 편지 숨김

Next.js Route Handler는 `GET`, `POST`, `PATCH`, `DELETE` 등의 HTTP 요청을 처리할 수 있다. 현재 범위에서는 NestJS의 독립적인 모듈, 컨트롤러, 프로바이더 계층과 별도 배포 단위를 추가해 얻는 이점보다 관리 비용이 더 크다.

### 5. 한 명이 개발하고 운영하기에 배포와 장애 지점이 적다

React 프론트엔드와 NestJS API를 분리하면 다음 관리 대상이 추가된다.

- 두 애플리케이션의 개발 서버와 빌드 설정
- 프론트엔드와 API의 별도 배포
- API 주소와 환경변수
- CORS 또는 프록시 설정
- 프론트엔드·백엔드 간 DTO와 타입 동기화
- 두 런타임의 로그, 오류 및 보안 업데이트

Next.js 단일 애플리케이션은 UI, 서버 요청 처리, 타입, 검증 규칙을 같은 저장소와 배포 흐름에서 관리할 수 있다. 이는 기능 수보다 운영 인력이 제한적인 현재 프로젝트에 중요한 이점이다.

### 6. 요구사항이 커지면 NestJS를 나중에 분리할 수 있다

Next.js를 선택한다고 해서 이후 백엔드 분리가 막히지는 않는다. 데이터 접근과 도메인 로직을 UI 및 Route Handler에서 분리된 모듈로 유지하면, 백엔드 요구사항이 커졌을 때 해당 로직을 NestJS API로 이전할 수 있다.

초기부터 가능성만으로 두 애플리케이션을 운영하지 않고, 실제 요구가 발생하는 시점에 분리한다.

## 검토한 대안

### React + Vite 프론트엔드와 NestJS API 모노레포

다음과 같은 복잡한 서버 도메인이 확정된 경우 적합하다.

- 여러 종류의 클라이언트가 하나의 API를 사용한다.
- 학생이나 운영자가 작품을 직접 등록·수정한다.
- 역할 기반 권한, 승인 과정, 파일 업로드가 필요하다.
- 알림, 실시간 기능, 외부 연동, 배치 작업이 많다.
- 프론트엔드와 백엔드를 별도의 팀이 독립적으로 개발한다.

현재 프로젝트에서는 NestJS가 주로 몇 개의 롤링페이퍼 API만 제공하게 된다. 이에 비해 배포, CORS, 타입 공유, 서버 운영 복잡도가 커지므로 선택하지 않는다. 또한 공개 작품 페이지를 React SPA로만 제공하면 정적 HTML과 메타데이터를 위해 별도 구성을 추가해야 한다.

### Next.js 프론트엔드와 NestJS API 모노레포

SEO와 독립 백엔드를 모두 확보할 수 있지만 현재 범위에는 가장 복잡한 구성이다. 서버 도메인이 충분히 커지기 전까지는 Next.js와 NestJS가 중복된 서버 계층을 갖게 된다. 독립 API가 실제로 필요해질 때 재검토한다.

### 완전한 정적 사이트

전시·작품 소개만 있다면 적합하지만, 롤링페이퍼 작성과 관리자 숨김 기능은 지속적인 쓰기 작업과 인증된 서버 처리가 필요하므로 선택할 수 없다.

## 단점과 대응

### 프론트엔드와 서버 코드의 경계가 흐려질 수 있다

Route Handler에 데이터베이스 로직을 직접 작성하지 않는다. 요청 파싱, 입력 검증, 서비스 로직, 데이터 접근을 분리해 NestJS 없이도 계층 경계를 유지한다.

### Client Component가 과도하게 늘어날 수 있다

페이지와 정적 콘텐츠 컴포넌트는 기본적으로 Server Component로 유지한다. 브라우저 API, 상태, 이벤트 핸들러가 필요한 가장 작은 컴포넌트에만 `use client`를 적용한다.

### 관리자 기능의 보안을 직접 고려해야 한다

관리자 페이지를 숨기는 것만으로 보호하지 않는다. 편지 숨김을 실행하는 서버 작업에서 인증과 권한을 다시 확인한다. 세션 쿠키는 `HttpOnly`, `Secure`, `SameSite` 속성을 적용하고 비밀값은 환경변수로 관리한다.

### 정적 페이지와 최신 편지 데이터의 캐시 정책이 다르다

작품과 작가 페이지는 정적 생성하고, 롤링페이퍼 조회·작성 요청은 동적으로 처리한다. 공개 편지 목록은 새 편지가 작성된 직후 반영되어야 하므로 정적 export만 사용하는 배포 방식은 채택하지 않는다.

## NestJS 재검토 조건

다음 조건 중 하나 이상이 실제 요구사항으로 확정되면 독립 NestJS API와 모노레포 전환을 검토한다.

- 관리자 기능이 작품·작가·전시 콘텐츠를 관리하는 CMS로 확대된다.
- 학생 계정, 운영자 역할, 승인 흐름 등 복잡한 인증·인가가 추가된다.
- 모바일 앱 또는 외부 서비스가 같은 공개 API를 사용한다.
- 이미지·영상 업로드와 변환 파이프라인을 서버가 담당한다.
- 실시간 알림, 메시지 스트리밍, 작업 큐, 예약 작업이 추가된다.
- 서버 도메인을 독립적으로 배포하거나 확장해야 한다.
- 백엔드를 전담하는 개발자가 추가된다.

단순히 API 엔드포인트 수가 늘어났다는 이유만으로 분리하지 않는다. 배포 독립성, 도메인 복잡도 또는 운영 조직의 변화가 발생했을 때 결정한다.

## 결과

### 기대 효과

- 작품 페이지의 정적 생성과 SEO를 기본 구조로 확보한다.
- 롤링페이퍼와 최소 관리자 기능을 별도 API 서버 없이 제공한다.
- 프론트엔드와 서버 사이에서 타입과 검증 규칙을 공유한다.
- 한 명의 개발자가 하나의 저장소와 배포 단위를 운영한다.
- 필요 이상의 초기 인프라를 만들지 않는다.

### 감수하는 제약

- Next.js의 Server Component와 Client Component 경계를 이해해야 한다.
- 관리자 인증, 입력 검증, 요청 제한을 애플리케이션 안에서 명확히 설계해야 한다.
- 서버 기능이 크게 성장하면 독립 백엔드로 이전하는 작업이 필요할 수 있다.
