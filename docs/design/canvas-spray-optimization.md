# Canvas 스프레이 성능 최적화 설계

- 작성일: 2026-09-08
- 기준 커밋: `cbc8a733e43ba43878bbae81aafa7f6b2f8bc0e9`
- 대상: 메인 Hero의 Canvas 스프레이 인터랙션

## 목표

입자 밀도, 위치, 반지름, 색상, 드립, 지속 시간과 페이드 결과를 유지하면서 빠른 드래그 구간의 메인 스레드 Canvas 렌더링 비용을 줄인다.

기준선에서 빠른 드래그는 Native 환경의 렌더 p95가 7.55ms, 프레임 간격 p95가 20.30ms였고 CPU 4× 환경에서는 각각 27.05ms, 38.00ms였다. 최대 활성 스탬프는 Native 733개로 측정됐다.

## 변경하지 않는 시각 규칙

- 스탬프 간격은 12 CSS px을 유지한다.
- 스탬프 하나는 중심 형태, 입자 82개와 선택적 드립으로 구성한다.
- 입자의 난수 분포, 크기와 알파 범위를 유지한다.
- 색상 팔레트와 스트로크 단위 색상 순환을 유지한다.
- 스탬프는 1.8초 동안 완전히 보이고 0.6초 동안 사라진다.
- Canvas DPR 상한은 2를 유지한다.
- 정밀 포인터가 없거나 reduced motion을 선호하는 환경에서는 비활성화한다.
- 성능을 위해 스탬프나 입자 수를 줄이는 적응형 품질 조절은 이번 범위에서 제외한다.

## 구현 방향

### 1. 결정론적 스탬프 모델

스탬프 생성 로직을 React 컴포넌트에서 순수 모듈로 분리한다. 난수 생성기를 인자로 주입해 운영 환경에서는 `Math.random`을 사용하고, 시각 회귀 테스트에서는 고정 시드를 사용한다. 같은 입력과 같은 난수열은 최적화 전후에 동일한 스탬프 데이터를 만들어야 한다.

### 2. 입자 경로 캐시

현재는 모든 프레임에서 모든 입자에 `beginPath()`, `arc()`, `fill()`을 반복한다. 스탬프 생성 시 입자를 알파 구간별 `Path2D`로 묶고, 렌더링 시 캐시된 경로를 스탬프의 위치로 이동해 채운다.

알파 값 자체를 임의로 양자화하면 픽셀이 달라지므로, 첫 구현에서는 원래 알파 값별 경로를 보존한다. 브라우저가 지원하는 `fill(path)`를 사용해 원 경로 생성만 제거하고 색상과 페이드 계산은 기존 값을 유지한다.

### 3. 프레임 내 불필요한 할당과 레이아웃 조회 제거

- 만료 스탬프는 `Array.filter()` 대신 제자리 압축으로 제거한다.
- Hero 크기는 `ResizeObserver`가 갱신한 값으로 렌더링한다.
- 렌더 루프에서 `getBoundingClientRect()`를 반복 호출하지 않는다.

### 4. 입력과 프레임 소비 분리

포인터 이벤트는 최신 좌표만 저장한다. 거리 보간과 스탬프 생성은 다음 animation frame에서 한 번 소비한다. 단, 이벤트 사이의 전체 이동 경로와 12px 간격은 누락하지 않아 기존 밀도를 유지한다.

입력 최적화는 렌더 캐시와 별도 커밋·측정으로 분리한다. 렌더 캐시만으로 목표를 충족한다면 시각·입력 회귀 위험이 더 큰 입력 변경은 적용하지 않는다.

## 검증 전략

### 구조 검증

- 고정 시드로 만든 스탬프의 직렬화 결과가 기준 fixture와 일치해야 한다.
- 만료 정리 전후의 순서와 생존 스탬프가 기존 `filter()` 결과와 일치해야 한다.
- 동일 경로를 소비했을 때 생성 좌표와 개수가 기준 구현과 일치해야 한다.

### 시각 검증

- 동일 좌표·고정 시드로 최적화 전후 Canvas를 캡처한다.
- 픽셀 차이 이미지와 차이 픽셀 비율을 저장한다.
- Native와 CPU 4× 빠른 드래그 영상을 각각 저장한다.
- 실제 임의 질감에서도 색상, 중심 형태, 외곽 입자와 드립을 육안 검수한다.

### 성능 검증

기존 E2E 스크립트와 동일하게 Idle, Click, Slow drag, Fast drag, Decay를 Native와 CPU 4×에서 각각 5회 실행한다. Run 01은 워밍업으로 분리하고 Run 02~05 중앙값을 대표값으로 사용한다.

비교 항목은 다음과 같다.

- 입력 이벤트와 생성 스탬프 수
- 최대 활성 스탬프 수
- Canvas 프레임 수
- 렌더 p50·p95·최댓값
- 프레임 간격 p50·p95·최댓값
- 16.7ms와 20ms 초과 프레임 수
- Canvas `arc()`·`fill()` 호출 수
- Long Task와 GC 이벤트
- GC 이후 heap 변화
- Renderer Main, Compositor와 GPU Process trace

## 증거 자료 구조

최적화 전 자료를 덮어쓰지 않고 다음 구조로 분리한다.

```text
performance/spray/
  baseline/                 기준선 메타데이터와 기존 결과 참조
  optimized/                최적화 배포 측정 원본
    artifacts/              시나리오별 metrics와 trace
    report/                 CSV, JSON, Markdown와 그래프
    evidence/
      screenshots/          Chrome Performance 및 화면 캡처
      videos/               Native·CPU 4× 실행 영상
      visual-diff/          고정 입력 전후 및 diff 이미지
  comparison/               전후 변화량 표·그래프·해석
```

모든 결과에는 Git SHA, 배포 URL, Chrome 버전, 기기, 논리 해상도, DPR, 주사율, 전원 및 throttling 상태를 함께 기록한다.

## 수용 기준

- 고정 입력 시 생성되는 스탬프 수와 입자 데이터가 기준선과 일치한다.
- 픽셀 비교 결과가 허용 오차 안에 있고 육안으로 밀도와 질감 차이가 없다.
- Idle에서는 스프레이 rAF와 Canvas 작업이 지속되지 않는다.
- Native와 CPU 4× 빠른 드래그의 렌더 p95 및 프레임 간격 p95가 기준선보다 개선된다.
- 개선 수치뿐 아니라 전체 반복 실행 범위와 원시 결과가 보존된다.
- 성능이 나아지지 않거나 시각 차이가 발생한 최적화는 별도 실험 결과로 기록하고 운영 코드에는 포함하지 않는다.
