# 통신이 느려도 작품을 고를 수 있도록

상태: 개선 브랜치 커밋·PR 검토용. 운영 반영 및 현장 재검증 전.

원격에서도 확인할 수 있는 [측정 기준 문서와 원시 자료](../../performance/2026-10-30-space-preview-resilience.md)를 별도 보존했다. 아래 artifacts 경로는 당시 로컬 기록 위치다.

## 1. 사용자 목적과 현장 근거

전시 사이트는 관람객과 전시 관계자가 작가·작품을 탐색하고 메시지를 남기는 서비스다. 관계자도 실제 사용자이며, 현장에서 관람객의 이용 상황을 접하는 제보자다. 사용자는 관계자로부터 네트워크가 좋지 않을 때 이미지 표시가 늦고, 메시지 작성란이 나타나지 않거나 메뉴 이동이 되지 않아 관람객이 불편을 겪었다는 이야기를 전달받았다. 제보의 빈도·발생률·관람객별 소요 시간은 집계하지 않았다.

2026-10-29 개발자가 현장 PC를 직접 조작하며 프로필 사진 지연과 지도 작품 미리보기 대기를 기록했다. `IMG_5491.MOV`는 지도에서 작품을 기다리는 장면, `IMG_5479.JPG`는 당시 Wi-Fi 환경 기록이다. 사진만으로 신호 품질이나 특정 요청의 병목을 확정할 수는 없다. 낙서 누적 시 버벅임은 별도 증상이며 네트워크와 같은 원인으로 묶지 않았다.

현장 재방문이 어려워, 동일 현장 개선 전후 결과 대신 **동일 코드·작품·브라우저 조건의 실험실 비교**를 구축했다. QA Hub 협업 도구 사례와 구분되는 전시 웹사이트 개선이다.

## 2. 먼저 해결한 범위와 판단

이번 범위는 **SPACE 지도에서 작가 선택 → 작품 식별 → 상세 이동** 하나다. 영상과 코드의 연결이 분명하고 DB를 변경하지 않고도 반복 검증할 수 있어 우선 선택했다. 가장 많은 사용자가 겪었다거나 사업 영향이 가장 크다는 근거는 아직 없다.

기존에는 이미지가 준비되기 전 작품명·작가명까지 함께 숨겼다. 네트워크 지연의 근본 원인을 확정하지 않더라도, 이미지 대기를 작품 식별 대기로 연결하는 구현은 코드로 확인할 수 있다. 관람객에게 필요한 첫 결과는 모든 이미지의 고화질 다운로드가 아니라 ‘어떤 작품인지 알고 다음 탐색을 결정할 수 있는 상태’라고 정했다.

선택하지 않은 대안:

- 최종 이미지를 일괄 저화질로 변경: 디자인 전시의 목적에 맞지 않아 제외했다.
- 모든 작품 선다운로드: 느린 연결에서 첫 진입 비용과 불필요한 전송을 늘릴 수 있어 제외했다.
- 전역 오프라인 앱·서비스 워커: 첫 방문 네트워크 단절까지 해결하지 못하며, 캐시 갱신 복잡도에 비해 이번 증상에는 범위가 크다.
- 프로필·메시지·메뉴·낙서를 동시에 변경: 서로 다른 원인을 분리하기 어려워 후속 과제로 남겼다.

## 3. 사실, 가설, 구현의 차이

| 구분 | 확인 내용 |
| --- | --- |
| 코드로 확인 | `space-map.tsx`는 hover/focus로 작품을 바꾸며 Next Image가 요청된다. 작품별 key로 이미지 노드를 분리한다. |
| 코드로 확인 | 기존 `previewContent` 전체의 opacity를 이미지 완료 후에만 1로 바꿔 제목과 작가명도 기다리게 했다. |
| 코드로 확인 | SPACE 이미지에 대응하는 작은 data URL이 기존 제출 자료 manifest에 이미 존재했다. 썸네일용 data URL과 구분된다. |
| 현장 원인 가설 | 연결 품질이 전송 대기를 늘렸을 가능성이 높다. 현장 요청 타이밍·TTFB·다운로드·디코딩은 측정하지 않아 병목을 확정하지 않는다. |
| 이번 변경 | 작품 정보와 SPACE 미리보기는 이미지 완료와 독립적으로 표시한다. 고화질 준비 시 이미지만 교체한다. |
| 이번 변경 | 2초 이상 기다릴 때 작은 하단 안내, 실패 시 명시적 재시도를 제공한다. 재시도 버튼을 포인터·키보드로 조작할 수 있다. |
| 유지 | 최종 `spaceImageSrc`, Next Image sizes/quality, object-fit, 카드 크기, 타이포, shade, 지도 좌표, 정상 hover 모션을 유지한다. |

`preview-load-state.ts`는 시도 번호와 loading/ready/error를 관리한다. 작품 변경은 기존 key를 유지해 새 노드로 분리하고, 재시도는 이미지 key만 바꾸며 이전 시도의 상태 변경을 무시한다. 임의 타임스탬프 URL이나 자동 무한 재시도는 넣지 않았다. 대기 안내 타이머는 닫힘·완료·언마운트 시 정리한다. 기존 숨겨진 첫 작품 이미지 요청 정책은 변경하지 않았다.

## 4. 검증 환경과 재현 방법

- 기준: Git `5328fc2`를 별도 디렉터리에 추출한 정상 Turbopack production build, 로컬 3101.
- 수정: `fix/space-preview-resilience`의 미커밋 작업본, 같은 방식의 production build, 로컬 3102.
- macOS 14.6 arm64, Node 24.4.0, pnpm 9.15.3, Playwright 1.61.1.
- Chromium 149.0.7827.55. WebKit은 macOS 14용 동결 엔진으로 기능 검사만 수행했다. 실제 iPhone/Safari 검증으로 표현하지 않는다.
- 1.64.1은 macOS 14 WebKit 초기화 프로토콜 오류가 있어 테스트 의존성만 1.61.1로 고정했다. [upstream 기록](https://github.com/microsoft/playwright/issues/42964).
- WebKit의 기본 Tab은 macOS 설정에 따라 링크를 건너뛴다. 재시도 후 다음 링크 이동은 해당 환경의 Option+Tab으로 검사했다. 제품이나 OS의 키보드 설정을 바꾸지 않았다. [Apple 문서](https://developer.apple.com/documentation/webkit/wkpreferences/tabfocuseslinks).
- 기존 webpack 빌드는 About CSS의 기존 전역 선택자 오류로 실패했다. 제품 코드를 우회 변경하지 않고, 기준본의 의존성을 독립 복사해 정상 Turbopack 빌드를 사용했다.

### 기능 검사와 성능 측정은 분리

`tests/e2e/space-preview.spec.ts`는 요청을 보류·실패시켜 동작을 검사한다. 이 routing 결과를 캐시나 실제 전송 속도 지표로 쓰지 않는다.

`scripts/performance/measure-space-preview.mjs`는 요청 interception 없이 Chromium CDP로 **지도 선택 구간만** 제한한다. 페이지 진입·폰트 로딩은 제한 밖이다. 정상/저속 × cold/warm 각 10회, 버전당 40회, 총 80회다. 한 번에 한 버전씩 실행한다.

- 저속: 다운로드 50,000 B/s(0.4 Mbps), 업로드 25,000 B/s(0.2 Mbps), latency 400ms, 패킷 손실 없음.
- 화면 1920×1080, DPR 1, 대상 윤이지 `3et`, 서비스 워커 차단, 서버 이미지 캐시 warm.
- cold: 반복마다 새 브라우저 컨텍스트, 대상 작품을 미리 열지 않음.
- warm: 같은 컨텍스트에서 대상 이미지를 한 번 연 뒤 다른 작품을 거쳐 재선택. 메모리 캐시 재사용 상황이며 cold와 섞지 않는다.
- 작품 정보 시간: 선택 이후 제목이 현재 작품이고 모든 조상 opacity가 0.99 이상인 첫 animation frame. 사람의 인지 시간을 측정한 것은 아니다.
- 고화질 시간: 위 조건과 이미지 ready 상태가 함께 충족되는 시점. 네트워크·디코딩·React 반영을 포함한 로컬 준비 지표다.
- 작은 미리보기: data URL 적용 시점을 기록한다. 실제 인지 가능성이나 이미지 디코딩 완료율로 표현하지 않는다.
- 20초 timeout과 실패를 원시 JSON에 남긴다. 중앙값은 10개 정렬 후 가운데 두 값의 평균이다.
- ResourceTiming 항목은 캐시 재사용 시 새로 남지 않을 수 있다. warm의 이전 로딩 항목을 재선택 전송량으로 계산하지 않는다.

실행 예:

```sh
pnpm exec playwright install chromium webkit
SPACE_TEST_URL=http://127.0.0.1:3102 pnpm exec playwright test
node scripts/performance/measure-space-preview.mjs --url=http://127.0.0.1:3101 --label=baseline --sha=5328fc2 --output=artifacts/space-preview/baseline.json --runs=10
node scripts/performance/measure-space-preview.mjs --url=http://127.0.0.1:3102 --label=candidate --sha=5328fc2+working-tree --output=artifacts/space-preview/candidate.json --runs=10
node scripts/performance/compare-space-visuals.mjs
```

두 서버와 빌드는 위 명령 전에 각각 준비한다. 운영 DB를 테스트 데이터로 쓰지 않는다. 결과와 스크린샷은 git 제외된 `artifacts/space-preview/`에 저장한다. 배포 버전의 CDN 상태나 현장 Wi-Fi를 재현했다고 해석하지 않는다.

## 5. 결과

아래는 각 조건 10회의 중앙값을 ms 정수로 반올림한 값이다. 원시 기록은 `artifacts/space-preview/baseline.json`, `candidate.json`이다. 기준본은 `5328fc2`, 수정본은 해당 기준 위의 미커밋 최종 작업본(`candidate-final`)이다. 최종 커밋 확정 시 식별자를 추가해야 한다.

| 조건 | 작품 정보: 이전 → 수정 | 고화질 준비: 이전 → 수정 |
| --- | ---: | ---: |
| 정상 / cold | 8 → 8 | 8 → 8 |
| 정상 / warm | 4 → 3 | 4 → 4 |
| 저속 / cold | 822 → 8 | 822 → 824 |
| 저속 / warm | 5 → 4 | 5 → 4 |

저속·첫 선택에서 정보 표시가 이미지 준비와 분리되었다. **고화질 전송 자체가 빨라진 결과는 아니다.** 이미 캐시된 작품은 이전 구현도 빨랐으며, 수 ms 차이를 의미 있는 사용자 개선으로 주장하지 않는다. 전체 80회에서 20초 timeout은 없었다. 한 작품·한 환경의 반복이므로 전체 작가나 실제 관람객의 개선율로 일반화하지 않는다.

비용과 보존 결과:

- 초기 HTML encoded body: 10,909 → 13,932 bytes(+3,023). 초기 동일 출처 script encoded body 합: 918,564 → 919,097 bytes(+533). 데이터 URL을 초기 화면에 포함하는 비용이며, 첫 페이지 진입 속도 개선을 주장하지 않는다.
- 선택 시 대상 이미지 ResourceTiming 신규 항목: cold는 양쪽 10/10회에 1개, warm은 양쪽 10/10회에 0개. warm에서는 이전 표시의 항목만 남는다. 이를 서버 전체 요청 건수로 해석하지 않는다.
- 최종 대상 이미지 URL 매개변수 `w=640&q=75`, encoded body 19,776 bytes로 동일하다. 임의 저화질 옵션을 추가하지 않았다.
- 정상 화면 비교: 400·822·1020·1350·1920·2560px 전체 페이지에서 변경 픽셀 **0**. 실제 모션 종료 후 캡처했으며 영역 마스킹은 하지 않았다. `scripts/performance/compare-space-visuals.mjs`, `artifacts/space-preview/visual/comparison.json`.
- 기능 E2E 22개 통과(Chromium 15, WebKit desktop 6, WebKit touch 1). 플랫폼에 해당하지 않는 26개 조합은 skip이며 통과 수에 포함하지 않는다. 지연 중 상세 이동, 오류/재시도, 역순 완료, 키보드, 모바일 직접 이동, 360~2560px 링크/overflow, reduced motion을 검사했다.
- 기존+추가 단위/회귀 검사 216개 통과. lint/type-check/production build 통과.
- 독립 리뷰에서 재시도 실행 후 키보드 초점 손실과 오류 카드의 링크 가림을 발견했다. 수정 전 각각 실패하는 테스트를 확인하고, 버튼 제거 전 원래 링크로 초점을 돌리고 버튼만 포인터를 받도록 변경했다. 19개 부스의 오류 상태 hit target과 실제 상세 이동, 키보드 재시도→Escape→다음 작품 이동을 두 엔진에서 재검사했다. 이후 전체 22개 E2E와 216개 회귀 검사가 통과했다. 경미한 미해결 리뷰 항목은 없었다.

개선 전 브라우저 검사는 이미지 보류 시 제목의 유효 opacity가 0이라 실패했고, 변경 후 같은 요구 검사가 통과했다. 이는 단순히 예쁜 로딩 화면을 추가한 것이 아니라 작품 식별 정보의 표시 조건을 바꾼 근거다. 대기·실패 스크린샷은 `artifacts/space-preview/pending.png`, `error.png`다.

## 6. 다음 검증

영상·스크린샷·trace·원시 지표를 보존하는 재현 도구와 실제 촬영 결과는 [Playwright 증거 기록](./2026-10-30-space-playwright-evidence.md)에 추가했다. 녹화는 기존 80회 비녹화 측정과 분리한다.

운영 반영은 별도 승인 후 진행한다. 실제 사용자 불편 감소, 탐색 완료율, 만족도, 현장 문제 해결 여부는 아직 확인하지 않았다. 운영에서는 이미지 오류·긴 대기 빈도를 개인정보 없이 집계할지 검토하고, 관계자에게 같은 탐색 동작을 다시 확인받는 것이 후속 단계다. 실험실 결과와 실제 사용자 결과를 구분해 기록한다.

## 실행 중 판단과 남은 비용

- 범위는 지도 탐색 하나로 좁혔다. 프로필·메시지·메뉴·낙서 문제는 남는다.
- 최종 quality/sizes를 보존했다. 고화질 준비 시간 자체를 단축하는 변경은 아니다.
- 초기에는 커밋·푸시·PR·배포 없이 로컬 증거를 보존했다. 이후 사용자 요청에 따라 논리 단위로 커밋하고 main 대상 PR로 제출한다. 병합·운영 배포는 별도 요청 전 수행하지 않는다.
- 기준본 외부 symlink의 Turbopack 제약 → webpack 시도 → 기존 About CSS 오류 확인 후 독립 복사한 정상 Turbopack 빌드로 전후 비교했다. 현장/Vercel CDN과 동일 환경은 아니다.
- macOS 14의 최신 Playwright WebKit 오류 때문에 테스트 버전을 고정했다. 현대 실제 Safari 검증은 남는다.
- 전후 측정은 테스트와 동시에 돌린 임시 실행을 버리고 직렬 재실행했다. 지도 선택 구간만 제한했으므로 첫 페이지 진입 성능은 입증하지 않는다.
- 오류 카드 전체의 포인터 차단을 없애고 버튼만 조작 가능하게 했다. 재시도 버튼으로 이동하는 시간을 임의로 제한하지 않도록, 오류 카드는 지도 내부에서 다음 선택·이탈·Escape·외부 focus까지 유지한다. 오류 카드가 잠시 남는 비용은 있다.
- 기존 숨겨진/모바일 첫 작품 eager 요청 정책은 변경하지 않았다. 이 정책의 트래픽 비용은 남는다.
- 작은 미리보기 적용은 기록했지만 관람객의 실제 인지율을 측정하지 않았다. 화면 캡처 확인과 인지 성과를 구분한다.
- WebKit의 다음 링크 이동은 기본 macOS의 Option+Tab을 사용했다. 다른 OS 키보드 설정까지 동일하게 검증한 것은 아니다.
