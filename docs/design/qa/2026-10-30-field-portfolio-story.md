# 포트폴리오 스토리 초안 — 통신이 느려도 작품 탐색을 이어가도록

개선 브랜치 커밋·PR 검토를 진행하는 범위의 초안이다. 운영 반영, 실제 관람객 효과, 현장 재확인은 아직 결과로 쓰지 않는다. 원격에서 볼 수 있는 원시 수치와 화면은 [측정 기준 문서](../../performance/2026-10-30-space-preview-resilience.md), 구현 근거·측정 한계는 [검증 기록](./2026-10-30-space-preview-resilience.md)에 남긴다.

## 한 문장

졸업전시 현장에서 접한 이미지 대기를 ‘연결 속도’만의 문제가 아니라 ‘작품을 식별할 정보까지 함께 기다리는 경험’으로 재정의하고, 최종 화질을 유지하면서 작품 정보를 먼저 제공하도록 개선했습니다.

## 이야기의 흐름

### 문제 — 출시 후 실제 사용 조건에서 드러난 탐색의 끊김

KNUD 졸업전시 웹사이트를 개발하고 전시장 안내 PC에서 운영했습니다. 전시 관계자로부터 연결이 좋지 않을 때 관람객이 이미지를 기다리거나 기능을 이용하는 데 불편을 겪는다는 제보를 받았습니다. 10월 29일 현장을 방문해 사이트를 직접 조작했고, 지도에서 작가를 선택한 뒤 작품 이미지가 나타날 때까지 기다리는 장면을 기록했습니다.

네트워크 상태가 유력한 원인 후보였지만, 당시 요청 단계별 시간은 측정하지 못했습니다. 따라서 ‘현장 Wi-Fi가 원인이었다’고 단정하지 않고, 코드에서 확인할 수 있는 대기의 구조부터 살폈습니다.

### 핵심 결정 — 다운로드보다 먼저 제공해야 할 결과를 정하기

기존 지도는 이미지 준비가 끝날 때까지 작품명과 작가명도 숨기고 있었습니다. 관람객의 목적은 고화질 파일을 내려받는 것 자체가 아니라 관심 있는 작품을 찾고 상세 내용을 살펴보는 것이었습니다. 이미지가 늦더라도 작품을 식별하고 다음 행동을 선택할 수 있어야 한다고 판단했습니다.

전체 이미지를 더 압축하거나 모든 작품을 미리 다운로드하는 대신, 지도 탐색 한 구간을 우선 개선했습니다. 전시의 시각적 완성도를 지키면서 효과를 분리해 확인할 수 있기 때문입니다. 이 선택이 피해 빈도나 매출 영향이 가장 크다는 의미는 아닙니다.

### 구현 — 기다리는 동안에도 탐색할 수 있는 상태

작품명·작가명과 기존 자료의 작은 미리보기를 먼저 표시하고, 고화질 이미지가 준비되면 같은 위치에서 교체하도록 분리했습니다. 오래 걸리면 진행 상태를 짧게 안내하고, 실패하면 작품 정보는 유지한 채 다시 불러올 수 있게 했습니다. 빠르게 다른 작가로 이동해도 이전 작품이 현재 정보에 섞이지 않도록 상태를 분리했습니다. 최종 이미지의 화질과 기존 정상 화면 디자인은 유지했습니다.

### 검증과 결과 — 현장 수치 대신 재현 가능한 비교를 남기기

전시 마지막 날이어서 개선 후 같은 현장 PC와 네트워크에서 다시 확인하기 어려웠습니다. 검증을 생략하는 대신 Playwright와 브라우저 네트워크 제한으로 현장에서 관찰한 지연을 재현하기 위한 통제된 저속 조건을 구성했습니다. 현장 속도를 실측한 것은 아니므로 같은 환경을 정확히 복제했다고 주장하지 않았습니다. 동일 작품·화면·브라우저에서 기존 코드와 수정 코드를 비교하고, 정상/저속 연결과 첫 선택/재선택을 구분해 조건별 10회씩 총80회 측정했습니다.

저속 연결(0.4 Mbps, latency 400ms)에서 처음 작품을 선택할 때, 정보 표시 중앙값은 약 822ms에서 8ms로 줄었습니다. 고화질 준비는 약 822ms와 824ms로 유사했습니다. 다운로드를 빠르게 만든 것이 아니라, 이미지 대기가 작품 식별을 막지 않도록 바꾼 결과입니다. 대기·실패·재시도 등을 브라우저 검사로 확인했고, 6개 화면 크기에서 정상 화면의 픽셀 차이가 없었습니다.

다만 초기 HTML이 약 3KB 늘어나는 비용이 있었습니다. 이는 로컬 제한 환경의 결과이며, 관람객 만족도나 현장 문제 해결률로 표현하지 않았습니다. 운영 반영과 사용자 재확인은 다음 단계로 남겼습니다.

## 최대 3장 안에서의 배치안

1. **서비스와 발견:** 제품 링크·본인 역할, 관계자 제보, 현장 영상 한 컷. 관람객의 목적과 ‘기다려야만 하는 탐색’을 제시한다.
2. **판단과 변경:** 왜 일괄 화질 저하 대신 정보 표시 조건을 바꿨는지 설명한다. 이전 대기 화면과 개선 대기 화면을 같은 크기로 보여준다.
3. **검증과 배움:** 822→8ms는 ‘작품 정보 표시’, 고화질 시간은 유사하다는 비교를 함께 적는다. 80회 조건, 정상 디자인 보존, 초기 응답 비용과 미확인 현장 결과를 짧게 남긴다.

이력서까지 합쳐 3장이라면 서비스·발견을 이력서의 프로젝트 설명에 압축하고 2~3번을 사례 두 장으로 쓴다. 기술 이름보다 **불안정한 환경에서도 사용자가 해야 할 행동을 이어가게 한 결정과 검증**을 중심에 둔다.

## 쓰지 않을 표현

- “현장 네트워크 문제를 해결했다” — 현장 원인과 재검증이 없다.
- “관람객 이탈률/만족도를 개선했다” — 실제 사용자 지표가 없다.
- “이미지 로딩을 99% 단축했다” — 바뀐 것은 작품 정보 표시 시점이며 최종 이미지 시간은 유사하다.
- “모든 네트워크 환경에서 사용 가능” — 최초 진입의 완전한 단절이나 다른 기능은 해결 범위가 아니다.
- “QA Hub 성과” — 이번 결과는 관람객이 사용하는 전시 사이트의 코드 개선이다.
