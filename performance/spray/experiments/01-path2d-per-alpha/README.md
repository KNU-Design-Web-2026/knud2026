# 기각 실험 01 — 입자별 Path2D 캐시

- 실행일: 2026-09-08
- 대상 빌드: `perf/canvas-spray-optimization`
- 환경: 로컬 production build, Chrome, 1512×982, DPR 2, Native CPU
- 시나리오: 10초 Fast drag 후 4초 소멸 대기
- 성격: 정식 5회 결과가 아닌 방향 판단용 1회 smoke test

## 가설

기존 렌더러는 활성 스탬프마다 입자 82개의 `beginPath()`와 `arc()`를 매 프레임 반복한다. 각 입자의 원 경로를 스탬프 생성 시 `Path2D`로 캐시하면 입자 수와 알파를 그대로 유지하면서 렌더 비용을 줄일 수 있다고 예상했다.

## 시각 결과

고정 seed `20260908`과 같은 CDP 입력 좌표로 기존 렌더러와 캐시 렌더러를 캡처했다.

- SSIM: `0.999881`
- PSNR: `57.715203dB`
- 육안 비교: 밀도, 위치, 반지름과 색상 차이를 구분하기 어려움

관련 자료는 `visual-diff/`에 원본·최적화 Canvas, 전체 화면, diff PNG와 두 실행 MP4로 보존한다.

## 성능 결과

| 렌더러 | Pointer moves | Canvas frames | Render p95 | Frame interval p95 | 20ms 초과 | Long Task |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 기존 `arc()` | 320 | 870 | 7.7ms | 19.7ms | 25 | 0 |
| 입자별 `Path2D` | 275 | 516 | 11.8ms | 43.7ms | 283 | 5 |

Path2D 렌더러는 입력 처리까지 늦어져 동일 시간에 수신한 pointer move가 45개 줄었다. 렌더 p95는 약 53% 증가했고 프레임 간격 p95는 약 122% 증가했다.

## 기각 이유

난수로 생성한 입자의 알파가 대부분 서로 달라 스탬프 하나에 거의 82개의 Path2D와 `fill(path)`가 필요했다. 반복 `arc()`는 없어졌지만 경로 객체 생성·보관과 Path2D 채우기 비용이 더해져 전체 성능이 악화됐다.

따라서 입자별 캐시는 최종 구현으로 채택하지 않는다. 다음 실험에서는 입자 개수와 위치는 유지하되, 화면에 표시 가능한 범위 안에서 알파 경로를 제한된 그룹으로 묶어 draw call을 함께 줄일 수 있는지 검증한다.
